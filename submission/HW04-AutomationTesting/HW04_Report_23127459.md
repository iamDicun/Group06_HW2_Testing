## 2. Human Review & Gap Analysis (Script Quality)

### 2.1. False Positive Analysis — Why Original AI Assertions Were Too Weak

The original AI-generated FR-05 tests had **6 critical assertion weaknesses** that caused false positives (tests passed when the SUT had real bugs). The refactored tests now correctly detect these bugs.

#### Weakness 1: `h1:visible` Filter Masked Duplicate `<h1>` Tags

**Original (WRONG):**
```typescript
await expect(page.locator("h1:visible")).toHaveCount(1);
```

**Problem:** The SUT has 2 `<h1>` tags. Both are visible. But `h1:visible` with `.toHaveCount(1)` may have passed due to timing — the second `<h1>` renders after products load. The original test checked too early.

**Refactored (CORRECT):**
```typescript
const allH1 = page.locator("h1");
const h1Count = await allH1.count();
expect(h1Count, `SUT co ${h1Count} the <h1>`).toBe(1);
```

**Why this catches the bug:** No `:visible` filter. Counts ALL `<h1>` in DOM. The SUT has `<h1>Danh sách sản phẩm</h1>` + `<h1>Hiển thị 5 sản phẩm</h1>` = 2 tags → FAIL.

#### Weakness 2: `toContainText("₫")` Passed for "VND"

**Original (WRONG):**
```typescript
await expect(card).toContainText("₫");
```

**Problem:** `toContainText` is a **substring match**. The SUT renders `"30,000,000 VND"`. This does NOT contain `"₫"`, so it should fail. However, the original test used `card` (the entire product card) which includes multiple `<p>` elements. If any text matched, it passed. The real issue: the assertion was on the wrong element.

**Refactored (CORRECT):**
```typescript
const priceText = await home.priceElements.first().textContent();
expect(priceText).toContain("₫");
```

**Why this catches the bug:** Targets the exact `<p class="text-red-500">` element. `"30,000,000 VND"` does not contain `"₫"` → FAIL.

#### Weakness 3: XSS Check Only Counted `<b>` Tags

**Original (WRONG):**
```typescript
await expect(home.resultLine.locator("b")).toHaveCount(0);
```

**Problem:** The SUT uses `dangerouslySetInnerHTML={{ __html: search }}`. When searching `<b>test</b>`, the `<b>` tag IS rendered. But the original assertion only checked `<b>` count — if the SUT rendered it differently (e.g., as `<strong>`), it would pass as a false positive.

**Refactored (CORRECT):**
```typescript
const boldCount = await home.resultLine.locator("b").count();
expect(boldCount, `XSS: tim kiem da render ${boldCount} the <b>`).toBe(0);
// PLUS: Check full body HTML for script injection
const bodyHtml = await page.locator("body").innerHTML();
expect(bodyHtml.includes("<script>")).toBe(false);
expect(bodyHtml.includes("alert(")).toBe(false);
```

**Why this catches the bug:** Both checks run. The `<b>` count check catches `<b>test</b>`. The body HTML check catches `<script>alert('xss')</script>`.

#### Weakness 4: Alt Check Used `toHaveAttribute("alt")` Which Passes for Empty String

**Original (WRONG):**
```typescript
await expect(img).toHaveAttribute("alt");
const altValue = await img.getAttribute("alt");
expect(altValue?.trim()).not.toBe("");
```

**Problem:** `toHaveAttribute("alt")` passes even when `alt=""` (attribute exists, value is empty). The second check `not.toBe("")` should have caught this, but it was in a `for` loop that may have short-circuited.

**Refactored (CORRECT):**
```typescript
const altValue = await img.getAttribute("alt");
expect(altValue?.trim(), `Anh #${i}: alt PHAI co text mo ta`).not.toBe("");
```

**Why this catches the bug:** Directly checks that alt text is not empty. SUT has `alt=""` → `"".trim() === ""` → FAIL.

#### Weakness 5: Missing Price Format Regex Check

**Original:** No regex check for price format.

**Refactored (NEW):**
```typescript
const regex = new RegExp("^[\\d,]+ ₫$");
expect(priceText).toMatch(regex);
```

**Why this catches the bug:** `"30,000,000 VND"` does not match `/^[\d,]+ ₫$/` → FAIL.

#### Weakness 6: No Test for `<script>` Tag Injection

**Original:** Only tested `<b>` tag, not `<script>`.

**Refactored (NEW):**
```typescript
await page.waitForLoadState("networkidle");
const bodyHtml = await page.locator("body").innerHTML();
expect(bodyHtml.includes("<script>")).toBe(false);
expect(bodyHtml.includes("alert(")).toBe(false);
```

**Why this catches the bug:** SUT renders `<script>alert('xss')</script>` via `dangerouslySetInnerHTML` → body contains `<script>` and `alert(` → FAIL.

## 4. AI Critique (200-300 words)

The original AI-generated FR-05 test suite contained **systematic false positives** caused by assertion patterns that were too lenient. The most critical failure was in **assertion specificity** — the AI used `toContainText("₫")` on the entire product card instead of targeting the price element directly, and `toHaveAttribute("alt")` which passes for empty strings. These weak assertions created a dangerous illusion of correctness: 42 out of 42 FR-05 tests passed on all 3 browsers, yet the SUT had at least 5 real bugs.

The root cause was that the AI **tested against specs rather than reality**. It wrote assertions assuming the SUT complied with FR-05 ("dùng ký hiệu ₫"), without verifying what the frontend actually renders. The AI never inspected `Home.jsx` to discover that the price element uses `"VND"` text, that `alt=""` is empty, or that `dangerouslySetInnerHTML` creates XSS vectors. This reveals a fundamental limitation: AI generates tests from *specifications*, but specifications describe *desired behavior*, not *actual implementation*.

After human review identified these gaps, I refactored with **targeted selectors** (`home.priceElements.first().textContent()` instead of `card`), **explicit value checks** (`altValue.trim() !== ""` instead of `toHaveAttribute("alt")`), and **regex pattern matching** (`/^[\d,]+ ₫$/` for price format). The refactored tests immediately caught 10 SUT bugs across 3 browsers that the original tests completely missed. The lesson: AI excels at generating test *structure* and *coverage matrices*, but human engineers must validate assertion *precision* — the difference between a test that runs and a test that actually catches bugs.
